# W0 evidence: Android (Vanadium) and iPhone (Safari 27)

Status: evidence only, 10 November 2026. Nothing in Sapflow was built or
changed. This note reports observations against
[the WHIP ingest design](../whip-ingest.md) (A0.1, A0.2, A0.3, A0.4, A0.5,
A0.7, A0.8) and does not edit it. Fixtures (addresses, ports, serials and
UDIDs removed; device models and build numbers generalised on purpose) are in `fixtures/whip/w0/vanadium-157-android-grapheneos/`
and `fixtures/whip/w0/safari-27-ios/`.

**Every Android result below is for Vanadium (Chromium-based, GrapheneOS),
not Chrome.** Chrome is not installed on the phone. The owner chose "test
Vanadium as-is", and nothing was installed. Treat these as Vanadium results.
Whether they transfer to Chrome on Android is not known.

An earlier version of this note, committed before the owner's go-ahead,
recorded that both phones were skipped. This version replaces it.

## Devices, versions and setup

| Item | Value |
|---|---|
| Android phone | Pixel on GrapheneOS, Android 17 (SDK 37). Vanadium (`app.vanadium.browser`) 157.0.8103.38, WebView 157.0.8103.38. The user agent is the reduced form: `Android 10; K`, `Chrome/157.0.0.0` |
| iPhone | an iPhone, iOS 27, Safari 27. Its user agent reads `Macintosh; Intel Mac OS X 10_15_7 ... Version/27` |
| Host | the M4 (Apple M4, macOS 26.6.2), load average from 5 to over 150 during the runs (other sessions). The phones were on the same /24 as the M4's `en0`, which the endpoint advertised |
| Tool | `scripts/whip-w0/phone-run.js` (new), the existing fake endpoint and play server, and `pages/` with small changes (below) |

Commands (from the repository root on the M4, `<lan-ip>` is its `en0`
address, ports 47200 to 47399):

```sh
ANDROID_SERIAL=<serial> node scripts/whip-w0/phone-run.js android capture udp|tcp --host <lan-ip> --range 47200-47399 [--port 47390] --out <dir>
ANDROID_SERIAL=<serial> node scripts/whip-w0/phone-run.js android loopback --runs ramp-a|ramp-b|opus --host <lan-ip> --range 47200-47399 --out <dir>
ANDROID_SERIAL=<serial> node scripts/whip-w0/phone-run.js android play --vendor <hls.js 1.7.4 dir> --range 47200-47399 --out <dir>
ANDROID_SERIAL=<serial> node scripts/whip-w0/phone-run.js android rotate --host <lan-ip> --range 47200-47399 --out <dir>
node scripts/whip-w0/phone-run.js ios capture|play --device <id> --host <lan-ip> --range 47200-47399 --out <dir>
```

Android pages open at `http://localhost:<p>/` over `adb reverse`, a secure
context, so the camera works; media goes over Wi-Fi to the M4. The iPhone opens
`http://<lan-ip>:<p>/` through `xcrun devicectl device process launch
--payload-url <url> com.apple.mobilesafari`, which worked. That page is not a
secure context, so the iPhone used synthetic media (a canvas and a stereo
WebAudio source).

Tool changes (small, all older runs unaffected): `fake-whip.js` and
`play-server.js` accept an HTTP bind host; `pages/loopback.html` has
`?source=camera` and a viewport meta tag and a full-width start button;
`pages/play.html` has `?quiet=1` (analyse decoded samples, send silence to the
speaker), a viewport tag and the larger button; `pages/capture.html` records
the candidates as gathered and no longer waits forever on
`AudioContext.resume()`, which Safari leaves pending without a gesture. New:
`phone-run.js`, `pages/rotate.html`, `pages/ios-play.html`.

## A0.3: TCP passive candidate (Vanadium)

Setup: the answer advertised only `tcp ... tcptype passive` on a relay port in
the 47200 to 47399 range, behind the byte relay. Every figure is from this
run.

| Item | Observed |
|---|---|
| ICE | checking at 3.6 s, connected at 7.2 s (page clock) |
| Selected pair | `succeeded`; local tcp **prflx active**, remote tcp host passive. `nominated` was false when sampled at 6 s |
| STUN over TCP | 31 valid checks, 8 with USE-CANDIDATE, 1 TCP connection |
| DTLS over TCP | ClientHello arrived as two RFC 4571 frames of 1200 and 263 bytes, identical in structure to desktop Chrome 157 |
| Local candidates | tcp host active (2, in the stats, not in the offer) and the peer-reflexive one |

## What Vanadium does not do: no UDP candidates

With the answer advertising only a UDP candidate, ICE never started:
`iceConnectionState` stayed `new`, no STUN reached the endpoint, no UDP
datagram arrived. `icegatheringstate` was `complete` before the POST. The page
saw one event, `end-of-candidates`; no candidate event was emitted at all.
`getStats` listed two `tcp host active` local candidates and no UDP one. The
offer contained no `a=candidate` lines. This was seen twice. Whether this is a
Vanadium or GrapheneOS default setting for WebRTC IP handling, or something
else, was not established, and no setting was changed. Because the same
holds for the in-page loopback, A0.4, A0.7 and A0.8 could not run as designed
(next sections).

## A0.4: rate ramp (Vanadium, real camera): not measurable

Two attempts (`ramp-a` and `ramp-b`, each a fresh page, real camera, H.264
preferred): both connections stayed `new`, the pair list had only `tcp host`
candidates, no receiver report was ever seen, and the sender sent nothing
(0 kbit/s for 30 s, no target and no available bitrate). The camera itself
worked and Chrome chose H.264. After two attempts the check was stopped, as
the brief says. No rate series exists for any phone.

## A0.7: Opus parameters (Vanadium): not run

Two attempts. Each loaded the page and waited at its start button for 4
minutes without posting a result, so there are no numbers. I did not find
out whether my tap missed the button or the page was waiting for something
else, so the cause is not established. A connection is needed anyway, and the
A0.4 attempts show there is none on this browser (the audio arms use the same
connect code), so a third try would not have helped. The A0.7 question for a
phone publisher is still open.

## A0.2: Opus playback

Method as on desktop (`pages/play.html`, a 14 s run per case, decoded samples
read through Web Audio, `?quiet=1` so the phone's speaker stayed silent,
hls.js 1.7.4 fetched into scratch and not kept). A "click" is a
sample-to-sample step above 0.07, against 0.035 for the tone itself.

### Vanadium 157 on Android

| Case | `currentTime` after 14 s | Media error | Audio decodes | Clicks (time since play) |
|---|---|---|---|---|
| hls.js, `av` | 14.02 | none | yes: 445 Hz left, 879 Hz right, no silent blocks, onset 398 ms | none |
| hls.js, `audio` | 14.02 | none | yes, onset 250 ms | none |
| hls.js, `av-preskip312` | 14.02 | none | yes, onset 343 ms | 1892 ms (0.39), 13502 ms (0.27), 13762 ms (0.50) |
| native, `recording` (MP4) | 14.02 | none | yes, onset 514 ms | none |
| native HLS, `av` | 13.86 | none | yes, onset 337 ms | 7599 ms (0.29), 12807 ms (0.45) |
| native HLS, `audio` | 13.99 | none | yes, onset 177 ms | 3598 ms (0.30) |

- No click in the first blocks after onset in any case (largest first-block
  step 0.0351, the tone's own). The 312 asset did not click at the start here,
  unlike Firefox on desktop; its click came 1.5 s after onset, and two more
  at the end of the window.
- Clicks in the native HLS cases came mid-playback, not at the start. Their
  cause is unknown and each was seen once; segment boundaries and a loaded
  phone are both possible. The clicks are provisional.
- `webkitAudioDecodedByteCount` does not exist in Chromium, so audio decoding
  rests on the Web Audio tap alone.
- `MediaSource.isTypeSupported('audio/mp4; codecs="opus"')` was true;
  `canPlayType` for native HLS was `maybe`.

### Safari 27 on iPhone (native HLS, muted)

The playback was **muted** (`muted playsinline autoplay`, one page load playing
each asset in turn), so a click cannot be heard and none was judged.
`webkitAudioDecodedByteCount` is not present in this Safari (the property is
undefined), so audio decoding could not be shown for any case.

| Case | Result |
|---|---|
| `av` (HLS, avc1 and Opus in fMP4) | `MEDIA_ERR_DECODE` (code 3, "Media failed to decode") about 12 ms after `loadedmetadata`; `currentTime` stayed 0 |
| `audio` (HLS, Opus only) | the same error |
| `av-preskip312` | the same error |
| `recording` (MP4, H.264 Main and Opus) | played without error, `currentTime` 10.05 at 10 s, 1280 px wide. Audio decoding not established |

`canPlayType('audio/mp4; codecs="opus"')` returned an empty string on this
Safari, `canPlayType` for HLS returned `maybe`, and `MediaSource` is not
defined in the page (hls.js could not be used, and was not needed).

## A0.8: rotation (Vanadium): partial, capture side only

The page stripped `urn:3gpp:video-orientation` from the answer (present in the
offer and in the unmodified answer, absent from the edited one). The in-page
loopback did not connect, so no frame was sent: `framesEncoded` 0, receiver
size 0 x 0 in all three phases. There is no receiver `frameWidth` or
`frameHeight`, and no decoded frame to judge. What was measured is the camera
track and the local preview:

| Phase | Display | Camera track and local preview |
|---|---|---|
| before | portrait (angle 0) | 720 x 1280 |
| after `user_rotation 1` | landscape (angle 90) | **1280 x 720** |
| after `user_rotation 0` | portrait | 720 x 1280 |

So, on Vanadium, the browser's capture side already delivers upright frames at
swapped dimensions when the display rotates. That is the capture, not what is
sent. Whether the encoder sends rotated pixels, or sends the same pixels with
a flag, is not shown, and it is the question A0.8 asks. Snapshots were taken
into scratch and not kept in the repository.

## Contradictions with, and additions to, `docs/whip-ingest.md`

1. **A browser may offer no candidates and gather no UDP.** Vanadium 157 did
   this. With only UDP candidates in the answer it never started ICE. A
   deployment whose answer has no TCP candidate cannot serve it. Chrome 157
   desktop offers TCP active candidates, and Vanadium connected over TCP at 47390;
   the design's TCP listener covers this, but as the only route, not just a
   fallback for blocked UDP. A0.3 is also the first result of that kind on a
   phone target.
2. **Safari's ClientHello is a single 216-byte datagram,** with a 38-byte
   `key_share` and no hybrid group, so the "two fragments" in the design
   describes Chrome, not every target. It still offers DTLS 1.3 and 1.2, the
   same suites and the same three `use_srtp` profiles as Chrome, so the design's
   DTLS 1.2 answer fits. Reassembly is needed for Chrome and not for Safari.
3. **Safari lists video before audio** (mid 0 video, mid 1 audio) and Chrome
   the reverse. Code must not assume section order.
4. **Safari's first H.264 is `640c1f` (High), and it has no Baseline.** The
   first-mode-1 rule selects High for Safari. A server that insisted on
   Baseline would refuse it.
5. **Safari also sends `0xc057`** in its connectivity checks, and one
   `a=candidate` per section is an mDNS name. The design's mention of
   `0xc057` as a Chrome attribute should say Safari too.
6. **All three targets offer `red/48000/2`** for audio, beside Opus. The
   design accepts only `opus/48000/2`, so it leaves `red` out of the answer,
   as intended.
7. **Native HLS on this iPhone does not decode Opus in fMP4** as packaged here
   (`dOps` pre-skip 0, `CODECS="avc1.4d401f,opus"`), in three of three cases.
   The design says whether every target player decodes Opus in fMP4 LL-HLS is
   tested, not assumed. The test result is that Safari on iOS does not, at
   least with this packaging, so a deployment needs a downstream transcode for
   that player. The recording as MP4 played, and its audio is not shown. A
   different packaging was not tried.
8. **Pre-skip 312 was not clicking at the start on Android** (it clicked later
   in one run). The design's note that 312 clicked at the start in Firefox is
   not extended to the phone.
9. The design's expectation that the phones' H.264 is "expected, not
   observed" is now observed for Vanadium and Safari on iOS. Chrome itself on
   Android is still not observed.

## What was changed on the phones, and how it was restored

**Android (Pixel on GrapheneOS):**

- Opened pages in Vanadium (`am start`, `VIEW` intents), about 14 loads. The
  tabs and history entries are still in Vanadium. The brief did not ask me to
  close them and I did not.
- `adb reverse tcp:<p>`: one per page, each removed on exit.
  `adb reverse --list` was empty at the end.
- Camera and microphone: the site prompt was answered "Allow this time" and
  the system prompts "Only this time". At the end `CAMERA` and `RECORD_AUDIO`
  for Vanadium were `granted=false`.
- Rotation: originals were `accelerometer_rotation=1` and `user_rotation=0`.
  Changed to 0 and 1, then `user_rotation` 0, then both put back to 1 and 0.
  Read back after restore: 1 and 0.
- Sent `KEYCODE_HOME` after each run. The phone ended on its launcher. The app
  that was in the foreground when I started was not reopened.
- Nothing installed. Screen timeout (30 minutes) unchanged. The phone warmed from
  33.3 C to about 38 C battery temperature and thermal status went 0 to 1
  (light) during the runs.
- `adb` momentarily lost the device twice and the server restarted once; I did
  not do that on purpose and another session may have. The device came back.

**iPhone:**

- Safari was launched five times with `devicectl ... --payload-url`: two
  A0.1 attempts hung (my page waited for `AudioContext.resume()`, which Safari
  leaves pending without a gesture), the third worked; two A0.2 launches, the
  first of which hung on a pending `play()` and the second worked. Each launch
  opened a page in Safari. Those tabs are still there, and Safari is as the
  runs left it. No settings were changed. I did not close any tab.
