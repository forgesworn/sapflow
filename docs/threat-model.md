# Threat model

What sapflow exposes, who can reach it, what could go wrong and what stops
it. Written at M5 (2026-10-20). Reassess when a protocol or a dependency
changes.

## What is exposed

| Surface | Who reaches it | Before authentication |
|---------|----------------|-----------------------|
| SRT, UDP 8890 | Anyone on the internet | Every datagram is parsed before the stream id is checked, by our own `sapflow-srt` |
| RTMP, TCP 1935 | Anyone on the internet | Handshake, chunk and AMF0 parsing by our own `sapflow-rtmp`, then the publish request |
| HLS, TCP 8888 | Viewers, normally through Caddy | Everything: HLS is public by design (v4v gates access in front) |
| Callback, outbound HTTP | Only to `SAPFLOW_CALLBACK_URL` | n/a |
| Publish authorisation, outbound HTTP | Only to `SAPFLOW_PUBLISH_AUTH_URL`, when set: one `POST` per publish attempt that passed the local throttle | n/a |
| Recordings directory | Local disk, shared read-only with v4v | n/a |

Assets: the stage (availability during a show), the publisher credential
(or, with `SAPFLOW_PUBLISH_AUTH_URL`, each gig's own key and the app's
publish-auth token), the callback token, the recordings, and the host.

## Attackers

1. **Anyone on the internet** with no credentials: crash or stall the server,
   guess the publisher password, fill the disk or memory.
2. **A viewer**, or many: exhaust connections or memory through HLS.
3. **The publisher** (credentialed, but an encoder can be compromised or
   buggy): send hostile media to crash the muxer, flood bandwidth, publish
   to someone else's stage path.
4. **The network between sapflow and v4v**: read or forge callbacks.

## Threats and mitigations

| # | Threat | Mitigation | Status |
|---|--------|------------|--------|
| T1 | One crafted UDP datagram crashes the server (found by fuzzing in `srt-protocol`, which served SRT until 2026-10-21) | Release builds unwind, so a panic ends one task. The datagrams that crashed `srt-protocol` are regression inputs for ours (`fuzz/regressions/own_srt_packet`). Our own `sapflow-srt` is built not to panic: no `unwrap`, `expect`, `panic!` or indexing outside tests (denied by lint), every length bounded by the datagram, stream id at most 512 bytes, at most 16 handshake extensions and 512 NAK entries per packet, timestamps and sequence numbers compared with wrapping arithmetic. Packets for a connection are taken only from the address that made it. | Fixed; packet parser, listener and connections after the handshake fuzzed clean (`own_srt_packet` 207 million inputs and `own_srt_listener` 4.2 million, 20 minutes each with overflow checks, no crash) |
| T2 | Crafted RTMP bytes crash the server or exhaust memory before authentication (fuzzing found two panics in `rml_rtmp`, the library used until 2026-10-20) | RTMP is now our own publish-only code (`sapflow-rtmp`): no indexing without a bound, no unchecked length arithmetic, nothing allocated from a declared length. Before the publish is accepted a connection may hold 1 MiB (unparsed input plus partial messages); after, 40 MiB. At most 64 chunk streams and 16 created streams; chunk size 1 to 16 MiB; AMF0 nesting 16 deep and 4,096 values per message. The handshake and publish request must arrive within 10 s in total, a PROXY protocol v2 header included on `SAPFLOW_RTMP_PROXY_ADDR`, where only `SAPFLOW_RTMP_TRUSTED_PROXY` (one address, no port) is read at all and the header is at most 536 bytes; that listener's port must be reachable only from the front, since anything else arriving from the front's address could name any publisher (`docs/trial-plan.md`). A panic would end only that connection's task (unwind). | Fuzzed clean (`rtmp_session` 4.7 million inputs and `amf0` 45 million, 20 minutes each, no crash); unit-tested per layer and against a recorded ffmpeg session |
| T3 | Hostile media from a publisher crashes or wedges the muxer | TS, PES, ADTS, Annex B, SPS: maintained crates, fed through code that drops bad packets and resyncs. FLV tags, AudioSpecificConfig, avcC and NAL lengths: our own small bounded parsers (h264-reader's avcC iterator panicked under fuzzing, so it was replaced). All fuzzed (`ts_ingest`, `flv_ingest`, `small_parsers`). A panic while muxing ends that publisher only; its path is released on drop. | Fuzzed clean |
| T4 | Publisher password guessing | 10 failures from one address in 60 s blocks that address for the rest of the window; constant-time comparison. With `SAPFLOW_PUBLISH_AUTH_URL` the app compares the key, and only its 401 or 403 counts as a failure here; a blocked address is refused before the app is asked. A 429 from the app (its own per-address throttle) refuses without counting. An app that is down, slow (3 s bound) or answers anything else refuses without counting, so an app restart cannot lock an encoder out, but it also means a guesser is not slowed by sapflow while the app is failing. | Done. Weak against many addresses: use a long random password or per-gig key |
| T5 | Taking over a live stage path | A second publisher on a live path is refused; only the configured publisher may publish at all, or with `SAPFLOW_PUBLISH_AUTH_URL` only a publisher the app admits for that path (v4v checks the key is that gig's own, so one gig's key cannot publish to another); paths must match `live/event-[a-z0-9-]+`. In that mode the synchronous entry point refuses outright, so a listener that skipped the app could not fall through to open publishing. | Done |
| T6 | Publisher floods bandwidth or memory | Bitrate cap per publisher (default 40 Mbit/s over 5 s); TS input buffer capped at 8 MiB; segment capped at 64 MiB (a stream with no keyframes is dropped); 10 s idle timeout. With `sapflow-srt`: a receive buffer of 8,192 packets (about 12 MB) per connection, filled no further (a packet beyond it delivers the oldest early; a jump past the whole buffer starts afresh rather than reporting everything between as lost); no packet held longer than its latency plus 1 s, whatever its timestamp says; at most 1,024 loss ranges tracked (the list is scanned per packet) and a drop request costs one pass over it; 16,384 payloads queued for the muxer, or the publisher is dropped; 5 s without a packet closes the connection. | Done |
| T7 | Many publishers or idle RTMP sockets | `SAPFLOW_MAX_PUBLISHERS` per protocol (default 16); RTMP connections capped at 4x that, and get 10 s to authenticate. `SAPFLOW_MAX_PRESENTATIONS` counts through the final stream owner (default 4x publisher limit, capped at 4,096; 64 by default). Shared encoded init/fragment capacities are admitted under `SAPFLOW_MAX_FRAGMENT_BYTES` (512 MiB default), once per backing through its final alias. A new stream is refused once the streams' projected windows, with an assumed window (at least a ninth of the mark) for each one still starting and for the newcomer, would fill 80% of it, or while eight are still starting, so a crowd of publishers is not admitted into a budget that will then refuse every stream's next part; `SAPFLOW_WINDOW_SECONDS` bounds each window by time, so a long keyframe interval multiplies it far less (never under seven segments: 30 s keyframes still keep 210 s). A publisher whose bitrate rises after admission can still fill the budget, and a crowd of unmeasured streams can hold the eight starting places for up to 20 s each. Close releases cached ingest after terminal drain; exhaustion preserves only an incomplete accepted recording prefix. Other buffers, metadata, allocation transients and kernel memory remain separate in [the resource contract](retained-media-contract.md). | Local admission and ownership correctness implemented; matched load qualification open |
| T8 | Slow-loris or connection floods on HLS | At most 20,000 HTTP connections; 60 s request-head and progress-reset idle timeouts; 64 KiB request buffer. Parked playlist/part waiting is limited to 3x target duration. Ready framed responses have a separate absolute `SAPFLOW_HTTP_BODY_TIMEOUT` (120 s default), including headers; progress cannot extend it. A turn yields after 16 write attempts. Responses share immutable backing charges but retain their own cursors/metadata; expiry drops application ownership while kernel queues remain separate. The open-file soft limit is raised to the hard limit at startup, with a warning if it stays low. | Local stalled/trickling/backpressure correctness implemented; sustained load and deadline scheduling qualification open |
| T9 | Path traversal through chunk names or stream paths | Chunk names must be `<prefix>_init.mp4`, `_seg<N>.mp4` or `_part<N>.mp4`, looked up in memory, never on disk. Stream paths are validated before use; recording paths are built only from validated paths and digits. Expiry deletes only `<digits>.mp4` files under `live/*/`. | Done, unit-tested |
| T10 | Recordings fill the disk | Recording does not start below `SAPFLOW_RECORD_MIN_FREE_GB` free (default 2) and stops, finishing its file, if free space falls below it mid-show; expiry after `SAPFLOW_RECORD_DELETE_AFTER` (default 7d); a recording that falls 50 s behind is abandoned rather than buffered in memory. A full disk stops recording, not streaming. | Done |
| T11 | Callback token exposed or callbacks forged | Plain HTTP by design: the callback must stay on the private network (as with mediamtx). The token is not logged. v4v refuses callbacks whose path does not match the prepared session. | Accepted risk; keep the callback off the public internet |
| T20 | A crash, SIGKILL, OOM kill or power cut loses the app's report of a recording, or a damaged outbox or recording file misleads or crashes recovery | Each recording's owed `recordSegmentComplete` is kept in `.sapflow-outbox` in the recordings directory from before its file is written until v4v answers 2xx, and sent at the next start. The directory is this user's and private (0700), entries are private (0600) regular files, nothing is followed through a symbolic link, writes are temporary file, fsync, rename, directory fsync, and a lock keeps a second sapflow out. Entries hold no URL or token; a malformed entry is never sent and expires. Interrupted files are parsed as untrusted bytes by a bounded scanner that reads only box headers and `moof` boxes (fuzzed, `recorded_prefix`), and are never rewritten. Recovered callbacks go one at a time, at most 60 a minute; failures are retried in rounds 30 s to 10 minutes apart, a round ending after three failures in a row, until delivered or expired. Delivery is at least once: a crash between v4v's 2xx and the entry's removal sends it again. If the outbox cannot be opened, sapflow logs an error and records and reports as before, without recovery. | Done, unit-tested |
| T17 | Publish authorisation exposed, forged or stalled | Plain HTTP only (`https://` is refused at startup: sapflow has no TLS client), so the request carries the publisher's key and the URL's token in clear: keep it on the private network, as with mediamtx's `authMethod: http`. Neither the URL nor the password is logged or put in an error; only the status or the kind of failure is logged, at debug, and refusals stay rate-limited (T13). One attempt, no retries, 3 s from connect to status; redirects are not followed; only the status line and headers are read (16 KiB at most), never the body. Anything but 2xx refuses. With `SAPFLOW_SRT_APP_KEYS` the 2xx may carry the stream's SRT passphrase, also in clear on that link; it is never logged and is dropped once the caller is answered. An RTMP connection waits for the answer inside its 10 s setup budget; SRT callers wait in their own admission task, still capped at `SAPFLOW_MAX_PUBLISHERS` awaiting or live. Refused alongside scoped publish sessions. | Done; accepted risk as T11 |
| T12 | Viewer privacy | No sessions, cookies or query strings in chunk URLs; viewer IPs are not logged. | Done |
| T13 | Log flooding with bad datagrams or refused publishes | `sapflow-srt` logs nothing (it counts what it drops); refused publishes are logged at most 20 a minute, with a count of those suppressed. | Done |
| T14 | Unmaintained dependencies | `srt-tokio`/`srt-protocol` (last release 2024-05) were removed on 2026-10-21 (M6c): SRT is our own `sapflow-srt`, whose only dependencies are maintained RustCrypto crates for encryption. RTMP no longer depends on `rml_rtmp` (2023-04): it is our own code. | Done |
| T16 | Spoofed-source SRT handshakes (the SYN cookie is meant to prove the client receives at the address it claims) | `srt-protocol` derives the cookie from the peer address and the current second with a fixed-key hash, so it can be computed by anyone; a spoofed handshake can get as far as access control. The stream id check and credentials still apply, and a spoofed source never receives the replies. `sapflow-srt` keys the cookie per process (the standard library's randomly keyed hash, `RandomState`, SipHash-1-3 at present; its algorithm is not guaranteed) over the peer address and port and the minute; it is valid for that minute and the next. A conclusion with a wrong cookie gets no answer, and nothing is allocated before a valid one. Its socket ids come from the same key, so they are not guessable either. At most 100 handshake packets a second are answered (bursts of 200) and at most twice `SAPFLOW_MAX_PUBLISHERS` connections, open or awaiting the policy decision, are held. | Fixed (`srt-protocol`, which was weaker here, was removed at M6c) |
| T15 | Supply chain | Few dependencies, all permissive licences (`THIRD_PARTY_LICENSES.txt`), `Cargo.lock` committed, `unsafe` forbidden in our crates. | Done |
| T18 | A publisher that changes its codec configuration at every keyframe, making a recording file and a `recordSegmentComplete` callback each (v4v takes 120 callbacks a minute from one address, for every stage) | HLS serves every epoch, but each stream's recording rolls from a budget (`SAPFLOW_RECORDING_ROLL_BURST`, default 8, regaining one per `SAPFLOW_RECORDING_ROLL_REFILL`, default 60 s, passed in both media time and wall time, so timestamps spaced faster than real time cannot refill it); past it epochs are served but not recorded, and the files on either side are marked `epoch-rate`. Ten minutes of an epoch every 2 s make 10 files. | Done |
| T19 | A captured SRT conclusion handshake replayed to take over a stage admitted by passphrase. The key material (salt and wrapped keys) crosses the network in clear, and an SRT claim replaces the live publisher. A copy of an attempt that never carried media only displaces the encoder; a copy of an admitted connection's handshake also restores that connection's keys, so whoever recorded it could send its media again and it would decrypt onto the stage (AES-CTR is unauthenticated, so predictable bytes can also be flipped) | Under `SAPFLOW_SRT_APP_KEYS`, when a caller with key material first connects, before the throttle, the app or any limit, it owns that key material by its address and caller socket id. The same key material from anyone else is refused there with `BADSECRET`, without asking the app or counting against the throttle (T4), so a replayer behind the encoder's own NAT cannot lock the encoder out; this holds however the owner's attempt ends (waiting for the app, throttled, refused by the app, admitted). The owner may resend; a caller about to be admitted has its key material recorded before the claim and refused to everyone from then on, the owner included. sapflow keeps a SHA-256 digest of the part of the key material the check binds (the salt half the key derivation reads, and the wrapped keys: editing the rest still passes the check, so it is no way round the guard): 16,384 owners in memory, and 128 admitted entries per stream path and 4,096 in all, in memory and in `SAPFLOW_SRT_REPLAY_STORE`, in separate tiers so a flood of owners cannot push out admitted entries; owners evict their oldest ended entry, a path its own oldest ended entry past 128, and past 4,096 in all the oldest ended entry of the path holding the most, so a tenant churning admissions on many streams of its own evicts only its own entries; never one waiting or open. A queued write already covered by a later one is skipped; a store from a newer sapflow is refused with its own message; a start that stopped before its first store landed starts again; stale temporary files are removed at start. The store is required with app keys, holds paths and digests of bytes sent in clear (nothing secret), is written atomically before each claim (a caller whose digest cannot be written is refused, nothing claimed), and an unreadable, malformed or removed store stops sapflow at start rather than starting empty. No time limit; lookups span paths; covers the app's passphrase and the global one. Refusals are logged rate-limited (T13) without key material or digest. Real encoders make fresh key material per connection, reconnects included (sapflow's caller; libsrt 1.5.1; OBS 32.0.4 after a dropped link and after a sapflow restart, checked 2026-11-13). | Done. Residuals: a copy that reaches sapflow before the original owns it, which takes an attacker who can delay or drop the encoder's packets, a passive listener with a faster route to sapflow, or one who times a copy while someone uses up the shared handshake allowance (100 a second); the effect is a displacement, repeatable while they win, with no media. A restart forgets owners, so an attempt refused before it can be replayed after it, again with no media. Admissions survive restarts while the store is intact; if the operator discards it, earlier admitted connections, media included, can be replayed until the app rotates those passphrases. Evicting an admitted entry, which takes 128 later admissions on its own stream, each needing that stream's passphrase, reopens media replay of that connection until the app rotates the passphrase; a full disk under the store stops every keyed SRT reconnect (fail closed); evicting an owner needs a flood of new key material from ended connections (minutes of every handshake the listener answers) and only displaces. An empty store created at start is logged as a warning, since after a first start it means the path does not persist. Callers the listener refuses before the application hears of them (`BACKLOG`, the handshake rate limit, a refused handshake) own nothing. An encoder that reused key material on a new connection would be refused, so Larix (not checked) and hardware encoders must be checked before turning app keys on. With the switch off the guard does not apply. The key is now checked before the claim there too, so a replay of a global-passphrase connection is the remaining way for an outsider to take over such a stage with only the stream id's credentials, and a replayed copy of an admitted connection also restores its keys, so its recorded media can be replayed onto the stage. Anyone who holds the shared global passphrase can already take over any stage whose clear stream-id credentials they have, so the guard would stop only outsiders there. Applying it would change what existing global-key deployments admit, so it waits on checking their encoders. Scoped publish sessions check the caller's key material against the session's passphrase and key length once its credentials match and before `reserve_claim`, so a wrong-key caller with a session's credentials spends no connection epoch, writes nothing to the session store and does not resume a stage held for reconnect (closed 2026-11-13); a live scoped stage was never open to takeover, its claim being reserved. Scoped sessions are now guarded too (closed 2026-11-13): a replayed copy of an admitted scoped connection, within the grant and while the stage is held, used to pass the check and resume the stage with its recorded media. The owner check runs at Connect as with app keys, and under the session manager's operation lock, once the key passes and before `reserve_claim`, key material that already admitted a connection is refused (`BADSECRET`, not counted) and otherwise remembered and written to the replay store, the claim waiting for the write (a failed write refuses the caller with nothing reserved). The admission task remembers without evicting and the SRT loop trims to the same bounds when the admission completes. The store defaults to `srt-replay` beside `SAPFLOW_SESSION_STORE`, whose private directory already outlives restarts, because a session restored after a restart may carry the same passphrase. The scoped residuals are the app-key ones above |

## Out of scope

- TLS: HLS is served behind Caddy, which terminates TLS. SRT control
  packets are never encrypted, so the stream id carries the publisher
  credential in clear, as mediamtx's form does, with or without a
  passphrase. `SAPFLOW_SRT_PASSPHRASE` (our own receiver only) encrypts the
  media (AES-CTR, which does not authenticate it); every caller must then
  use it, and a wrong one is refused and counted as a failed login (T4).
  `SAPFLOW_SRT_ENCRYPTION=optional` also admits callers that send no key
  material, whose media then crosses the network in clear; an encrypting
  caller still needs the right passphrase. Publish credentials, not the
  passphrase, decide who may publish in either mode.
  Its salt and wrapped key travel in clear, so a weak passphrase can be
  guessed offline: use a long random one. Hiding the credential itself
  needs a VPN.
- Denial of service by volume (raw bandwidth floods): the network's job.

## Known gaps, next steps

- Run vMix against sapflow (OBS and Larix have published over both
  protocols; `docs/interop.md`).
- Run the fuzz targets for hours, ideally in CI (the longest run so far is 20
  minutes per target).
- SRT encryption hardening from the M6b review (2026-10-21), all low:
  rate-limit only failed in-session key messages, so a forged one (which
  needs a spoofed address and the socket id) cannot delay a key refresh;
  reject retransmissions older than the previous key switch once a key
  slot is reused; check whether libsrt expects a reply to a key message
  that only retires the old key.
